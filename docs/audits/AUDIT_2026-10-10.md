## Critical

### 1. A turn can be given a one-second deadline, then forfeited

**What.** Every game write that sets `turnDeadline` only checks that the new deadline is after `request.time` and under 48 hours. The forfeit rule then lets either player end the game once `request.time` is past that deadline, and the winner must be the opponent of `currentTurn`.

**Why it matters.** The comment at the create rule says the future-timestamp check stops an instant forfeit. It stops a deadline that is already in the past. It does not stop a deadline one second in the future. A custom client can hand the opponent a one-second clock and then take the win. The 15-minute cron would also forfeit that game on its own. The normal app sets 24 hours. The rules do not.

**Where.** `firestore.rules` create path around line 1183, and the same `> request.time` / `< 48h` pair on the update paths (lines 1385, 1518, 1658, 1741, 1838, 2016, 2075). Forfeit is the update at line 1917. The red-team test `rules-tests/games-turndeadline-redteam.rules.test.ts` covers the year-9999 upper bound.

**Fix.** On every path that writes `turnDeadline`, require it to be at least about 23 hours ahead (the product window, with a little skew). Add a rules test that denies a deadline of one second and of one hour.

### 2. One account can move a dispute tally without casting a real extra vote

**What.** Creating a `disputeVotes` doc does not require the dispute's `landVotes` or `bailVotes` to go up in the same write. Deleting that doc does require the matching counter to go down by one. The same shape exists for clip votes.

**Why it matters.** Community review is binding. The cron in `api/cron/resolve-expired-disputes.ts` decides the letter from those counters. A client can file a vote document that does not increment the counter, then delete it in a write that decrements the counter. Repeating that drains a tally. The comment above the dispute update rule explains why the decrement exists (so a delete-and-revote cannot stuff the ballot). The missing half is that the create is not forced to increment.

**Where.** `firestore.rules` `disputeVotes` create (about line 3498) versus delete (about line 3532), and the dispute tally update (about line 3407). Clip votes are the same pattern around lines 3153 and 3217.

**Fix.** Require the matching counter to be exactly +1 in the same write as the vote create (`getAfter` on the dispute, verdict on the new vote doc). Add a rules test for a bare create followed by a paired delete. The referee should also be able to count vote documents if the counters and the documents ever disagree.

## High

### 3. Clip moderation is optional at the rules layer

**What.** A user clip may be created as `moderationStatus: 'active'` with no `moderation` field, or as `pending` with `moderation: 'pending'`. The app picks which one via `isClipModerationEnabled()`. The upload screener returns immediately unless `moderation == 'pending'`. Storage also lets the owner write straight into `approvedClips/{uid}/`.

**Why it matters.** PR #650 correctly hides pending and rejected clips from other readers. It does not force a new clip through that queue. The production bundle has the client flag **off** (`isClipModerationEnabled` is compiled to `parseFlag(undefined)`), which matches today's "clips go live immediately" behavior. The hole shows up the day the flag is turned on: a custom client can still publish an unscreened clip, and that write can also bump `clipsPosted`.

**Where.** `firestore.rules` user-clip create, lines 3056–3064. `src/services/clips.userWrites.ts` (the `moderationOn` branch). `functions/src/moderation/runUpload.ts` (`runUploadModeration`). `storage.rules` `approvedClips`.

**Fix.** While moderation is on, the rule should allow only the pending shape. Put that switch in the rules (a config doc both the client and the rules read), and stop client creates on `approvedClips/`. Let the function copy a file there after it passes.

### 4. The landed-claim dispute window is still optional

**What.** `matchResolutionPinsOk` still allows the old instant role-swap: matching goes straight back to setting, letters unchanged, no `pendingReview`. The comment says to keep it until the freeze-first client has rolled out, and says the current client still uses the instant arm.

**Why it matters.** The shipped client and `e2e/game.spec.ts` already freeze a landed claim in `pendingReview` and give the setter 24 hours to accept or dispute. A custom client can still skip that window, so the setter never gets a say. The production referee flag is off, so this community window is the only dispute path.

**Where.** `firestore.rules` lines 993–1007. The freeze arm starts at line 1008.

**Fix.** Remove the instant-swap arm now that production is on the freeze client. Add a rules test that denies it.

### 5. Turn history is a free-form field that becomes lifetime stats

**What.** Rules only limit how many history entries can be added (one per write, cap 200). They do not check `landed`, `letterTo`, `matcherUid`, or the video URL inside the new entry. `deriveGameStats` trusts those fields for tricks landed, letters, clean wins, comeback wins, and, when XP is on, land XP.

**Why it matters.** A player can append a history entry that claims lands they did not make. Stats close-out is idempotent (a game cannot award twice), and clients cannot write `xp` or `wins` on their user doc. The inputs those functions trust are still client-written.

**Where.** `firestore.rules` `turnHistoryGrowthOk`. `functions/src/applyGameStats.ts` `deriveGameStats`. `src/components/TurnHistoryViewer.tsx` plays history video URLs.

**Fix.** On each resolution branch, pin the new entry's `landed`, `letterTo`, and `matcherUid` to the transition being written. Have the viewer ignore video URLs that fail `isFirebaseStorageUrl`.

### 6. `createdAt` is chosen by the client, and the server trusts it

**What.** User create and game create do not pin `createdAt` to `request.time`. Report auto-hide uses `users.createdAt` for the 24-hour reporter-age gate. `applyGameStats` uses both timestamps for its anti-farm age check and for game duration.

**Why it matters.** Three fresh verified accounts that backdate `createdAt` can look old enough to count as trusted reporters, and a short game can look long enough to earn XP once XP is on.

**Where.** `firestore.rules` user create and game create. `functions/src/moderation` reporter age. `functions/src/applyGameStats.ts` `oldEnough`.

**Fix.** Require `createdAt == request.time` on create and unchanged on update. On the server, prefer the Auth user's creation time for the age gate.

### 7. A finished game can be deleted before stats are applied

**What.** A player may delete a game once `status != 'active'`. `applyGameStats` returns `"missing"` when the document is gone, and `onGameCompleted` does not set `retry: true`.

**Why it matters.** The loser can finish the game and delete it before the trigger commits `statsApplied`. The loss never lands. A trigger that fails once, even without a delete, also never retries, because the game does not change again. The in-transaction `statsApplied` check already makes a retry safe.

**Where.** `firestore.rules` line 2088. `functions/src/index.ts` `onGameCompleted` (about line 40). `functions/src/applyGameStats.ts`.

**Fix.** Allow delete only when `statsApplied == true` (keep the account-deletion admin path, which bypasses rules). Turn on function retry, or add a cron for terminal games whose `statsApplied` is not true.

### 8. The lobby listener can hide a game that is your turn

**What.** `subscribeToMyGames` runs three queries (`player1Uid`, `player2Uid`, `judgeId`), each `limit(20)`, with no `orderBy` and no status filter. The page size starts at 20 (`GAMES_PAGE_SIZE`).

**Why it matters.** Firestore returns an arbitrary 20 documents when there is no `orderBy`. A player with a long history can have an active game fall outside that page. The client forfeit sweep only sees games in this list, so that game sits until the cron, and the player may not see it.

**Where.** `src/services/games.subscriptions.ts` lines 172–174. `src/context/GameContext.tsx` line 51.

**Fix.** A separate listener for `status == 'active'` (ordered by `updatedAt`), plus a paged history query. Add the composite indexes those queries need.

### 9. Signup accepts passwords Firebase will reject, and the rejection becomes a Sentry issue

**What.** The form requires 6 characters and shows a strength meter. Firebase Auth on this project requires a number and rejects passwords over 20 characters. The error code `auth/password-does-not-meet-requirements` is not in `getAuthErrorMessage` or `BENIGN_AUTH_CODES`, so the raw Firebase sentence is shown and the exception is sent to Sentry.

**Why it matters.** A normal signup mistake looks like an outage. This audit produced that path once, and Sentry opened **SKATEHUBBA-SENTRY-4** for it (`FirebaseError: Missing password requirements: [Password may contain at most 20 characters, Password must contain a numeric character]`). The client said the password was "Fair".

**Where.** `src/screens/AuthScreen.tsx` (length check around line 126). `src/utils/helpers.ts` `pwStrength`. `src/utils/authCodes.ts`. Live: https://skatehubba.com/auth.

**Fix.** Match the client rules to the Firebase policy (8–20 characters, must include a number — confirm the exact policy in the console). Map the code to a plain sentence and add it to `BENIGN_AUTH_CODES`. Resolve SKATEHUBBA-SENTRY-4 after that, so the noise does not stay open.

### 10. Production App Check token exchange returned 403 from this network

**What.** The production client has App Check enabled. Every signup and sign-in from the audit browser logged `AppCheck: 403` and then `appCheck/throttled` for 24 hours. Auth still answered (the password-policy error, then successful signup), so Firestore/Auth enforcement did not block account creation.

**Why it matters.** If real browsers also get this 403, App Check is failing closed in the SDK even while enforcement is in monitor mode, and the 24-hour throttle means later tokens are not even attempted. If only datacenter or headless traffic gets the 403, the finding is that the reCAPTCHA key rejects this class of client, which is expected, and the console noise should be confirmed in Sentry before treating it as a user-facing outage. `enforceAppCheck` on the callables is hard-coded `false` (`functions/src/index.ts`).

**Where.** Live console on https://skatehubba.com/auth. `src/firebase.ts` `installAppCheck`. `docs/APPCHECK_ROLLOUT.md`.

**Fix.** Check Sentry and the App Check metrics for `403` / `initial-throttle` from real user agents. Confirm the reCAPTCHA key's allowed domains include `skatehubba.com`. Keep enforcement off until that 403 rate is near zero.

### 11. Roll Dice cannot finish a match once stats are written

**What.** `writeStats` reads one player's `diceStats` doc, writes it, then reads the other player's doc inside the same transaction. The Admin SDK rejects a read after a write. The handler tests use an in-memory fake that does not enforce that rule.

**Why it matters.** Quit and timeout both call `writeStats`. Those calls throw, the match stays open, and `diceSweep` skips it every run. The 10-active-match cap then fills up. The production **client** flag is off, so the website does not show Dice. The function is in the approved set and will hit the first match once `DICE_ENABLED` or a tester uid is turned on.

**Where.** `functions/src/dice/handlers.ts` `writeStats` (lines 185–206). `functions/src/dice/store.ts` `runTransaction` uses a real `tx.get` / `tx.set`.

**Fix.** Read both stats documents, then write both. Teach the fake to throw on a read after a write.

## Medium

### 12. The cookie banner sits on top of the bottom navigation

**What.** The banner is `fixed bottom-0 z-50`. The nav is `fixed bottom-0 z-40`. On a fresh session the banner's Privacy Policy control intercepted taps on the Challenge tab until OK was pressed. The Privacy Policy control in that banner measured 76×17 CSS pixels.

**Why it matters.** Home, Clips, Challenge, Map, and Me are all under the banner until the visitor answers. Challenge is the primary action. A 17px-tall link also misses the 24×24 CSS minimum for a target (WCAG 2.2, 2.5.8; the app otherwise aims at 44px).

**Where.** `src/components/ConsentBanner.tsx` (the fixed region). `src/components/BottomNav.tsx` line 73. Live lobby on a first visit.

**Fix.** Anchor the banner above the nav (`bottom` = nav height + safe area), or raise the nav while the banner is open. Give the Privacy Policy control a 44px hit area.

### 13. White text on brand orange is 2.86:1

**What.** `#ffffff` on `#ff6b00` is 2.86:1. That is the primary button and the raised Challenge disc. Normal text needs 4.5:1. Large or bold text needs 3:1, and 14px is not large text under WCAG even when it is bold. White on the lighter gradient stop `#FF8533` is 2.43:1.

**Why it matters.** Lighthouse's contrast audit scored 100 on `/` and `/auth` and did not list these buttons. The ratio is still under the AA threshold for the label "show me", "Create Account", and the white icon on the orange Challenge disc (non-text contrast needs 3:1).

**Where.** `src/index.css` brand orange. `src/components/ui/Btn.tsx`. `src/components/BottomNav.tsx` (the raised disc). `src/components/onboarding/tutorialSteps.ts` (`primaryCtaLabel: "show me"`).

**Fix.** Use near-black text on the orange fills, or darken the orange until white clears 4.5:1. Re-check the Challenge disc at 3:1.

Muted body text is fine: `#888` on `#0a0a0a` is 5.58:1, and `#8f8f8f` on `#141414` is 5.70:1.

### 14. The public deletion page points at the lobby

**What.** https://skatehubba.com/data-deletion tells a signed-in person to scroll to the bottom of the lobby for "Download My Data" and "Delete Account". Those controls are at the bottom of Settings. The privacy policy already says Settings.

**Why it matters.** A store reviewer or a user following the public page will not find deletion. The in-app path itself is real: Settings → Account → Delete Account, backed by `POST /api/account/delete` (recent login, then admin erasure, then Auth delete).

**Where.** `src/screens/DataDeletion.tsx` lines 28–38. `src/screens/Settings.tsx` around line 720. Live: https://skatehubba.com/data-deletion and https://skatehubba.com/settings.

**Fix.** Say Settings, not the lobby. Same sentence in any store questionnaire.

### 15. One verified account can decide a binding dispute

**What.** `classifyVerdict` treats a single land or bail vote as the result. Zero votes auto-accepts the claim. The vote rule requires a verified email and excludes the two players. It does not require account age.

**Why it matters.** A second account that has verified email decides the letter. Report auto-hide already has a reporter-age gate. Dispute votes do not.

**Where.** `src/services/dispute.resolution.shared.ts` `classifyVerdict`. `firestore.rules` dispute vote create.

**Fix.** Require a minimum number of votes, and the same minimum account age used for reporters. Until then, treat a one-vote result as a known weakness of the binding window.

### 16. The forfeit cron can spend its whole run on frozen games

**What.** Games in `pendingReview` or `communityReview` keep a `turnDeadline` that is already in the past. The sweep loads the oldest 100 active games past their deadline and then skips the frozen ones. `MAX_PER_RUN` is 100.

**Why it matters.** Enough frozen games and a real expired turn is never reached. Each skip is a transaction read, every 15 minutes.

**Where.** `api/cron/sweep-expired-turns.ts`.

**Fix.** Clear or push `turnDeadline` when a game freezes, or query `phase in [setting, matching]` so frozen games are not in the page.

### 17. Game clips and dispute videos are not tied to the game

**What.** A game clip can be created without `email_verified` or `notBanned()`, and its video URL only has to be some file in the bucket. A dispute's `matchVideoUrl` is not required to equal the game's `matchVideoUrl`. Report auto-hide and the admin keep/remove callable act on `source == 'user'` clips.

**Why it matters.** A banned user with a second account can post a game clip the admin tools do not hide. A setter can send the community a different video than the one played.

**Where.** `firestore.rules` game-clip create (about line 2976) and dispute create (about line 3336). `functions/src/moderation`.

**Fix.** Require verified email and `notBanned()` on game clips. Pin the URL and `turnNumber` to the game document. Extend auto-hide and the admin callable to game clips. Pin dispute `matchVideoUrl`, `setVideoUrl`, and `trickName` to the game.

### 18. Charter and coverage have drifted from the October features

**What.**

- Charter §4.14 says the cron endpoints write only transitions a client could have written. `api/cron/resolve-expired-disputes.ts` writes `xp` and `level`, which the rules forbid clients to write.
- Charter line counts are stale: `firestore.rules` is 3,582 lines (the charter still says 3,335).
- TOTP, XP levels, the full-screen clips player, and the DSA receipts/appeals shipped after the charter's feature list.
- `functions/src/moderation/handlers.ts` has no test. `functions/` and `api/` have no coverage floor. CI's e2e job does not set `VITE_FEATURE_EXTRAS_ENABLED`, so `e2e/map.spec.ts` and `e2e/clip-voting.spec.ts` skip. Extras are on in production.
- `npm run check:file-length` reports 14 files over the soft budget. The largest are `src/screens/Settings.tsx` (606), `src/screens/Landing.tsx` (506), and `src/components/map/AddSpotSheet.tsx` (405).

**Why it matters.** The next person who trusts the charter will think XP writes are illegal on the server, and the surfaces that are live in production are the ones CI never opens.

**Where.** `docs/CHARTER.md` §4.14 and §4.5. `.github/workflows` e2e job. `functions/src/moderation/handlers.ts`. `vite.config.ts` coverage `include`.

**Fix.** Amend §4.14 so XP awards are an approved server-only write. Turn extras on for one e2e job. Add a handlers test for the admin clip decision. Coverage for `api/` and `functions/` needs a maintainer decision because it touches CI config.

### 19. A few other game-logic gaps

- After a tied community vote, the dispute id is still `{gameId}_{turnNumber}`, so the setter cannot raise a second dispute on the retry (`src/services/disputes.raise.ts`).
- `onGameCompleted` runs on every game update and bails out unless the game just ended. That is cheap, and a failed run is the case finding 7 covers.
- The XP backfill script writes opponent and spot totals without the markers the live function uses, so a later rematch can count again (`scripts/backfill-xp.mjs`). Owners can also delete their own `xpMarkers` (`firestore.rules` around line 848).
- A judge "missed" ruling notifies the matcher that it is their turn to set, while the setter is the one on the clock (`src/services/games.judge.ts`).
- Both players tapping rematch at once creates two games (`src/App.tsx`).

### 22. Store readiness, secrets, and what is already in good shape

**Store.** Sign in with Apple is compiled off on the website (`isAppleSignInEnabled` is `parseFlag(undefined)`). The iOS release workflow sets the flag on. Google is offered on the web and in the app, so an iOS binary built without that flag would miss App Store 4.8. Native account deletion throws if `VITE_APP_URL` is unset (`src/services/auth.ts`). The iOS workflow sets it. `PrivacyInfo.xcprivacy` is present. Camera, microphone, photo, and location strings are in `Info.plist` and `AndroidManifest.xml`. `docs/STORE_PRIVACY_ANSWERS.md` is still marked draft, and it leaves Mapbox telemetry and nearby-spot queries as open questions. **Secrets and headers.** No service-account JSON or private key is tracked. `.env.example` holds placeholders. Production CSP is strict (`script-src` has no `unsafe-inline`; `frame-ancestors 'none'`; HSTS preload; `X-Frame-Options: DENY`). Cron routes check `Authorization: Bearer` against `CRON_SECRET` with `timingSafeEqual` and fail closed when the secret is missing (`api/cron/sweep-expired-turns.ts`, `resolve-expired-disputes.ts`, `drain-push-dispatch.ts`).
